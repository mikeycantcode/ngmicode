## Intended approach
WATCH stores `ks.version(key)`, and EXEC compares it again. The starter has two bugs.

1. **ABA on versions.** Versions are per-key counters. `removeEntry` deletes the counter and
   `flush` clears the map, so a key that is deleted and re-created starts again at version 1.
   `SET k` (v1) → WATCH (1) → `DEL k` (counter dropped, 0) → `SET k` (1) → EXEC sees 1 == 1 and
   commits. The fix draws stamps from a single global, monotonically increasing sequence, which
   is what the README says the design is. Either keep tombstone stamps for deleted keys, or bump
   them on delete and flush. Any scheme where a key's observed value can never repeat is fine.
   A bounded alternative: keep a global "epoch" for flush plus tombstones only for keys that are
   currently watched.
2. **Expired-but-not-reaped watched keys.** `watchedKeysChanged` compares versions without first
   running lazy expiry. A key whose TTL elapsed but that nobody accessed still carries its old
   version. The fix calls `ks.expireIfNeeded(key)` before comparing, and the removal bumps the
   version. Bug 1 must be fixed too, or the expiry removal resets the version.

## Key files
- `src/core/keyspace.ts`: `bump`, `removeEntry`, `flush`, `version`.
- `src/commands/transactions.ts`: `watchedKeysChanged`, WATCH handler.
- README "Transactions" section: documents the intended global-sequence design.

## Traps
- Fixing only incident 1. Hidden test 2 (the expired lease) still fails.
- Fixing only incident 2 by adding `expireIfNeeded`. The deleted key then has its counter
  removed, so the version drops to 0, which differs from the watched value and happens to abort.
  The DEL+SET case (test 1) and FLUSHALL+SET (test 3) still commit.
- "Fixing" by aborting EXEC whenever a watched key is missing or has a TTL. That makes EXEC abort
  spuriously; hidden test 4 checks untouched keys, including a non-existent watched key.
- Comparing values instead of versions. The re-created key has the same value, so that approach
  fails the ABA case.

## Strong signals
- The candidate writes failing tests first, with two sessions and a `ManualClock`, mirroring both incidents.
- The candidate names the problem: ABA on a reused counter. They notice the README and the code disagree.
- The candidate discusses the memory trade-off of tombstones (or their alternative) as the prompt asks.
- The candidate verifies there are no spurious aborts.

## Weak signals
- The candidate patches symptoms in EXEC, such as special-casing DEL.
- The candidate lets the agent rewrite WATCH to snapshot values.
- No explanation of why the version repeated.

## Follow-up questions
- Your fix keeps a stamp for every key ever deleted. How would you bound that memory without reintroducing ABA?
- Should WATCH on a key that expires abort EXEC? What changed in Redis 6.0.9 here, and why?
- How would WATCH interact with replication, where a replica applies a DEL generated by the primary's expiry?
- Can a session's own writes between WATCH and MULTI abort its own transaction? Is that desirable?
